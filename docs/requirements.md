| 项 | 值 |
| --- | --- |
| 文档版本 | v1.0（第一阶段） |
| 状态 | 待评审 |

## 1. 背景与目标

门诊业务的核心矛盾不是"把表单存进数据库"，而是**资源有限、角色众多、状态严格、并发真实**：

- 号源是有限资源，并发预约必须不超卖；
- 一份病历会被多人先后打开，必须能发现冲突而不是静默覆盖；
- 处方一旦签署就产生法律与审计意义上的责任，状态不能随意回退；
- 药房库存同时服务发药、退药、盘点，任何一次扣减都必须可追溯、可补偿。

MedFlow 以"一次完整的门诊就诊"为主线，把 **预约 → 签到 → 接诊 → 病历签署 → 开方 → 审方 → 发药/退药** 串成可运行的业务闭环，并在每个环节实现真实企业系统需要的并发控制、幂等、审计与补偿。

### 1.1 成功标准

1. 五类角色可以各自登录，看到属于自己的菜单，只能操作被授权的按钮与接口。
2. 一名患者从预约到发药可以完整走通，期间所有状态变化都有审计记录。
3. 50 个并发请求抢 1 个号源，**恰好 1 个成功**，其余收到明确的业务错误。
4. 两名医生同时编辑同一份病历，后提交者收到 409 冲突并拿到最新版本，不丢数据。
5. 库存不足时发药整体失败，不出现部分扣减；失败后库存可对账一致。
6. 每个模块都有自动化测试覆盖其核心规则，`mvn test` 与 `pnpm test` 全绿。

## 2. 角色与职责

| 角色 | 角色码 | 典型职责 | 数据范围 |
| --- | --- | --- | --- |
| 系统管理员 | `ADMIN` | 用户、角色、权限、科室、审计查询 | 全院（不授予临床操作权限） |
| 医生 | `DOCTOR` | 接诊、写病历、下诊断、开处方、结束就诊 | 本科室；本人排班与本人接诊 |
| 护士 | `NURSE` | 患者建档、签到分诊、查看候诊队列 | 本科室 |
| 药师 | `PHARMACIST` | 审方、发药、退药、药品与库存维护 | 全院处方与药房 |
| 收费员 | `CASHIER` | 挂号收费、退号退费、患者建档 | 本科室收费窗口 |

> 角色与权限是**多对多**关系；数据范围由角色上的 `data_scope` 声明（`ALL` / `DEPT` / `SELF`），取用户所有角色中最大的范围。

### 2.1 职责边界（防止权限膨胀）

- 管理员默认**没有**任何临床数据权限（`patient:read`、`emr:read` 等），需要显式授予；这是医疗信息系统的合规基线。
- 医生只能对**自己接诊**的就诊记录执行开始/结束/签署，数据范围 `SELF` 用于写操作校验。
- 药师可以读取全院处方，但不能修改处方内容，只能改变处方审核/发药状态。
- 收费员不能改病历，也不能发药。
- 任何角色都不能绕过状态机直接改 `status` 字段；后端只暴露业务动作接口。

## 3. 权限模型

### 3.1 权限粒度

| 类型 | 说明 | 前端表现 | 后端表现 |
| --- | --- | --- | --- |
| `MENU` | 菜单/页面访问 | 侧边栏与路由守卫 | 页面数据接口的读权限 |
| `BUTTON` | 页面内动作 | 按钮/菜单项隐藏或禁用 | 对应写接口的权限注解 |
| `API` | 纯接口权限（无 UI） | 无 | 方法级鉴权 |

权限码统一为 `模块:资源:动作`，例如 `appointment:create`、`emr:sign`。菜单权限同时承担路由访问控制。

### 3.3 菜单树

```text
工作台                     （所有角色）
科室人员                   schedule:read（医生/护士/收费员）
科室管理（只读）           system:dept:read（所有角色；编辑按钮需 system:dept:manage）
医生工作站                 encounter:read（医生/护士）
预约挂号                   appointment:read（医生/护士/收费员）
排班管理                   schedule:read（医生/护士/收费员；编辑需 schedule:manage）
病历模板（ADMIN）           emr:template:manage
系统管理（ADMIN）
├── 用户管理                system:user:read
├── 角色权限                system:role:read
└── 审计日志                system:audit:read
```

后续模块会按同一模式追加「临床业务」「药房」「收费」等菜单：菜单权限由后端 `sys_permission` 驱动，前端不硬编码角色。

后端 `GET /api/v1/auth/me` 返回当前用户、角色、权限码、数据范围与菜单树；菜单树由**权限表**按角色过滤生成，前端不硬编码角色。

## 4. 功能需求

### M1 基础框架与权限体系

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| FR-M1-01 | 用户名 + 密码登录，签发访问令牌与刷新令牌 | 正确凭据返回 token 与用户信息；错误凭据返回统一 401，不泄露账号是否存在 |
| FR-M1-02 | 刷新令牌轮换 | 旧刷新令牌使用一次后失效；重放旧令牌返回 401 并吊销该会话 |

| FR-M1-05 | 用户/角色/科室管理 | 管理员可增改停用；用户名唯一；不能删除内置管理员 |

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| FR-M6-01 | 药品目录 | 药品编码唯一；规格、单位、剂型、价格、处方类型可维护；停用不影响历史处方 |

| FR-M6-09 | 补偿 | 发药失败释放预占；取消/过期释放预占；补偿动作幂等且有审计 |

## 5. 关键业务规则汇总

1. **状态只能通过动作改变**：所有业务对象的状态迁移在领域层以显式映射表实现，`status` 不出现在通用更新 DTO 中。
2. **写操作三件套**：鉴权（角色 + 数据范围）→ 幂等（业务键唯一）→ 事务（状态 + 业务数据 + 审计 + 流水）。
3. **并发优先级**：数据库原子条件更新 > 唯一约束 > 乐观锁 > 分布式锁。本项目不使用 Redis 分布式锁保证正确性，Redis 只做缓存、草稿与会话。
4. **金额**：`DECIMAL(10,2)`，人民币，不做浮点运算；退款金额不得超过原单。
5. **时间**：服务端时间为准，统一 `Asia/Shanghai`，存储 `DATETIME(3)`。
6. **逻辑删除只用于主数据**；业务单据、审计、库存流水禁止删除。
7. **病历与处方快照**：签署/提交后保存 JSON 快照与 SHA-256，展示以快照为准，避免主数据变更影响历史。

| 性能 | 号源查询 P95 < 200ms；预约写入 P95 < 300ms（50 并发） | k6/JMH 脚本 + 集成测试基准 |
| 正确性 | 不超卖、不重复、不超退、不负库存 | 并发集成测试（Testcontainers） |
| 安全 | BCrypt(12) 存储密码；JWT 短期令牌；接口鉴权 100% 覆盖；越权测试 | 安全测试用例 + ArchUnit 注解检查 |
| 隐私 | 日志脱敏身份证/手机号；不记录病历正文；审计只记必要字段 | 代码审查 + 日志断言 |
| 可用性 | 后端启动 < 20s；健康检查区分 DB/Redis；失败返回可读中文错误 | Actuator + 冒烟脚本 |
| 可维护性 | 模块内分层，模块间只经应用服务/事件交互；行覆盖率 ≥ 70%（领域层 ≥ 85%） | ArchUnit + JaCoCo |
| 可测试性 | 领域规则纯单元测试；业务闭环集成测试；前端 Store 单测 | CI 全绿 |
| 兼容性 | Chrome/Edge 最近两个大版本；桌面优先，最小宽度 1280px | Playwright 冒烟（后续） |
| 可观测性 | 请求 ID 贯穿日志与响应；关键动作结构化日志；审计可查询 | 日志断言 |

## 7. 非目标（明确不做）

- 不做真实临床决策支持、诊断推荐、处方推荐；诊断与药品均为演示数据。
- 不接入真实 HIS/LIS/PACS、医保结算、支付网关、短信/微信。
- 不实现住院、手术、急诊、体检等院外流程。
- 不做微服务拆分与 Kubernetes 部署（单体 + Docker Compose 已足够表达业务）。
- 不做多租户；单院区模型，科室为数据隔离维度。
- 不追求像素级视觉设计，界面以信息密度与可用性优先。

## 8. 术语表

| 术语 | 含义 |
| --- | --- |
| 号源 | 某医生某时段可被预约的一个名额 |
| 排班 | 医生某日某半天出诊计划，包含多个号源 |
| 签到 | 患者到院确认就诊，预约转为候诊 |
| 接诊 | 医生开始本次诊疗，进入就诊中 |
| 主诊断 | 本次就诊的主要诊断，结束就诊必填 |
| 预占 | 处方审核通过后锁定库存但尚未实物出库 |
| FEFO | First Expired First Out，先过期先出 |
| 幂等键 | 客户端生成的唯一请求标识，重复请求返回首次结果 |
| 数据范围 | `ALL` / `DEPT` / `SELF`，决定查询与写操作可见范围 |
